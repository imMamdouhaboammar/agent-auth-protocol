# AgentAuth v0.2 Authorization Evaluation Algorithm

## 1. Goal

This document defines a deterministic security-oriented evaluation sequence for one AgentAuth Action Intent.

It does not mandate one implementation architecture.

## 2. Inputs

Required inputs:

- verified AgentAuth Context
- normalized Action Intent
- active grant or Direct Entitlement
- Subject Authority
- Agent Local Authority
- Provider Policy result
- Runtime Authority
- Approval Evidence when required

## 3. High-level algorithm

```text
authorize(context, intent):

  verify identity context
  verify intent binding
  resolve authority mode

  if delegated:
      verify grant active
      verify Subject matches grant
      verify Agent matches grant
      verify Instance accepted
      verify capability covers intent
      verify grant chain attenuation

  if direct:
      verify Direct Entitlement covers intent

  resolve Subject Authority
  resolve Agent Local Authority
  evaluate Provider Policy
  evaluate Runtime Authority

  if any positive authority layer does not cover intent:
      DENY

  if Provider explicit deny matches:
      DENY

  if an obligation is unsatisfied:
      STEP_UP

  if Approval Evidence is present:
      recompute Action Digest
      verify approval
      verify approval unconsumed
      verify approval unexpired

  reevaluate all relevant policy

  ALLOW
```

## 4. Capability matching

A Capability matches an Action Intent only if:

1. Action identifiers are equal
2. target Resource is in the Capability Resource set
3. Argument Constraint Map accepts the exact Action arguments
4. all authority-bearing extensions are recognized and valid

Unknown extensions deny.

## 5. Delegation-chain verification

For every parent-child pair:

1. verify issuer trust and grant authenticity
2. verify parent active
3. verify Subject continuity
4. verify allowed delegation
5. verify child lifetime attenuation
6. verify depth attenuation
7. verify every child Capability covered by parent
8. verify Constraint Subsumption
9. verify revocation freshness

A verifier MAY cache validated prefixes subject to revocation policy.

## 6. Provider relationship evaluation

Subject Authority MAY be generated by Provider-local relationship policy.

The AgentAuth evaluator consumes the resulting authorization facts.

It MUST NOT accept a self-declared relationship as equivalent to Provider-derived authority.

## 7. Decision object

Example allow:

```json
{
  "decision": "allow",
  "reason_codes": [
    "IDENTITY_VERIFIED",
    "GRANT_ACTIVE",
    "CAPABILITY_MATCHED",
    "SUBJECT_AUTHORITY_MATCHED",
    "PROVIDER_POLICY_ALLOWED"
  ],
  "matched_capability_id": "cap_17",
  "policy_version": "policy_42"
}
```

Example step-up:

```json
{
  "decision": "step_up",
  "reason_codes": [
    "HUMAN_APPROVAL_REQUIRED"
  ],
  "obligations": [
    {
      "type": "human_approval",
      "bind_to_action_digest": true,
      "expires_in_seconds": 300
    }
  ],
  "policy_version": "policy_42"
}
```

## 8. Denial reasons

Reason codes SHOULD distinguish:

- identity failure
- inactive grant
- Capability mismatch
- Resource mismatch
- Constraint failure
- Subject Authority failure
- Agent Local Authority failure
- Runtime restriction
- explicit Provider deny
- missing approval
- invalid Approval Evidence
- unknown authority-bearing extension

Reason codes MUST NOT leak sensitive policy details to unauthorized callers.

## 9. Evaluation consistency

A Provider SHOULD evaluate all security inputs from one logically consistent snapshot where practical.

For irreversible operations, avoid a large gap between:

```text
authorization decision
and
side effect
```

The business transaction SHOULD recheck critical mutable conditions or use atomic application controls.

## 10. Race conditions

Examples:

- grant revoked after evaluation
- account frozen after approval
- transaction limit consumed concurrently
- one-time approval replayed by two requests

Protocol authorization alone cannot eliminate every application race.

Providers MUST use atomic domain controls for counters, balances, inventory, and one-time effects.

## 11. Caching

Safe cache candidates:

- static Capability parsing
- public keys
- non-sensitive relationship graph prefixes
- validated chain structure

Risk-sensitive freshness applies to:

- revocation
- account status
- transaction limits
- step-up state
- fraud signals
- one-time Approval Evidence

## 12. Fail closed

The evaluator denies when it cannot prove coverage.

There is no "best effort" authorization mode for protected actions.

## 13. Conformance properties

Independent implementations SHOULD agree on:

- Capability syntax
- exact Action and Resource matching
- core Constraint checks
- core Constraint Subsumption
- closed-world argument behavior
- grant attenuation
- Action Digest computation

Provider-specific policy outcomes may differ because local policy is intentionally outside the portable core.
